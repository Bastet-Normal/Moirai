# 📖 Moirai - 全自动网文小说生成 Agent 系统

基于 **OpenAI 兼容协议**的本地小说创作工具，使用多个模型角色协作完成策划、正文、质检和状态维护。面向单用户、本机运行，不是可直接公网部署的多人服务。

**Moirai** 是产品及用户界面的正式名称。为保证已有作品、事务恢复和本机锁兼容，部分磁盘目录与内部日志仍保留历史 `novelengine` 标识；它们不是对外品牌，也不应手工改名。

系统采用**角色分工 + 动态状态机 + 伏笔账本 + 节拍式分段扩写 + 逻辑质检**降低长篇生成中的一致性风险；这些机制不保证文学质量、绝无设定错误或百万字叙事连贯，发布前仍需作者审核。

## 🌟 核心特性与架构

> 当前工程采用分层 Python 架构：HTTP 契约位于 `api/`，长任务位于 `services/`，工作流位于 `pipeline/`，领域状态与基础设施位于 `core/`，浏览器资源位于 `web/`。完整设计与数据不变量见 [ARCHITECTURE.md](ARCHITECTURE.md)。

### 1. 如何降低设定冲突？

* **动态状态机与背包管理**：实时跟踪主角与配角的境界等级、所在位置、伤势、掌握功法、背包道具与好感度。
* **剧情伏笔账本（Foreshadowing Ledger）**：自动登记埋下的悬念线索（`PLANTED -> DEVELOPING -> RESOLVED`），并在后续分卷与章节中调度回收。
* **分层滚动上下文**：每章生成时只精准注入`宏观总纲` + `中观分卷目标` + `前3章滚动事件摘要` + `本章登场角色的实时卡片`。

### 2. 如何控制正文节奏与文风？

* **节拍式扩写（Chunked Beat-Writing）**：拒绝一次性吐出 3000 字概括文。将单章拆解为 3~4 个独立微节拍（*压抑/危机 $\to$ 蓄力准备 $\to$ 爆发打脸 $\to$ 结算收益/断章留钩*），每节单独扩写。
* **反 AI 味词库与修辞准则**：严禁“深吸一口气”、“嘴角勾起一抹弧度”、“眼中闪过一丝复杂”等 AI 烂俗模板，强制采用微动作、场景破坏和短促对白推动。

## 🚀 快速开始

### 1. 安装依赖

推荐用仓库内的哈希锁文件创建隔离环境，以获得可复现安装：

```bash
uv venv .venv
# Windows: .venv\Scripts\activate
# macOS/Linux: source .venv/bin/activate
uv pip sync requirements.lock
```

只需快速体验时也可以安装兼容版本范围：

```bash
pip install -r requirements.txt
```

### 2. 配置环境变量

首次配置时复制 `.env.example` 为 `.env`（已有 `.env` 时直接编辑，不要覆盖）：

```bash
copy .env.example .env
```

编辑 `.env` 文件，配置您的 API 信息（以 DeepSeek 或 OpenAI 兼容中转为例）：

```ini
# OpenAI 兼容协议配置
OPENAI_API_KEY=sk-your-actual-api-key
OPENAI_BASE_URL=https://api.deepseek.com/v1

# 模型路由 (默认全部使用 deepseek-chat 或 gpt-4o / claude-3-5-sonnet 等)
DEFAULT_MODEL=deepseek-chat
WRITER_MODEL=deepseek-chat
PLANNER_MODEL=deepseek-chat
CRITIC_MODEL=deepseek-chat
STATE_MODEL=deepseek-chat
```

单页工作台内置：沉浸阅读器（字号调节、段落微手术、整章编辑、**细纲手动编辑**、**AI 段落定向重写**——选中任意段落给指令只重写该段）、机器质检轨迹与**正文版本绑定的人工审阅**、实体力导向图谱（含关系边自动提取）、思维树分支推演、伏笔账本、可编辑的人物卡与策划案、情绪心电图、短剧分镜与演播分配、商业宣发交付包、**发布前合规自查与一键替换**（低俗/血腥/涉政/极限词四类词库，命中可定位正文并批量替换），导出 TXT / Markdown / **EPUB** / **完整项目备份 zip**（含快照/图谱/记忆全部数据，可导入恢复）；支持亮/暗双主题、实时生产进度与日志、单章重写（质检多轮未过自动落库得分最高版本）、作者确认的历史状态修复、时光机回滚、回收站恢复与项目管理；API 配置支持按角色拆分模型（主笔/策划/质检/状态）与**质检严格度三档**（苛刻/标准/宽松），保存会以事务方式同步 `.env`、进程配置和当前模型客户端，任一步失败都会整体回滚；顶栏实时显示本次会话 **token 用量**。分支推演支持**一键采纳回写细纲**；合规词库支持**自定义违禁词**（界面增删、持久化、参与全书扫描）。CLI 新增 `python main.py config` 查看配置与用量。

现在还包括：可选叙事文风真正贯通策划、细纲、主笔与润色；新总纲明确每卷的全局首尾章节，大纲到达边界时只在所属卷内滚动规划（默认每次至多十章），并在卷首、卷末和全书终章使用相邻卷与全书终局约束；历史章节重写后按章重放人物、道具、图谱和伏笔事件；手动改正文后显式提示状态校准，并可在阅读器里只提取状态而不重写正文；备份安全校验、原子化项目持久化与 Web/CLI 跨进程作品锁；章节正文按需加载，项目状态、章节元数据和语义记忆分片存储，长篇续写不再反复重写全部旧正文。全本导出按需合并，不再每保存一章就重写整本。批量任务遇到失败会停在故障章，不会跳章污染时间线。浏览器依赖均已本地化，创作台运行时不依赖 Tailwind、字体或图谱库 CDN。

短剧分镜、读者推演、剧情分支、有声配置和商业宣发均视为可重建的派生结果，而不是独立事实。策划案、世界观、人物、细纲或正文发生实际变化时，状态事务会按真实输入范围同步撤下受影响的内存结果和磁盘文件；相同来源的重复保存不清空仍有效的结果。正文已经入库但后续短剧转换失败时，旧短剧也不会继续冒充新版结果。细纲只影响对应章节的分支推演，正文修改只撤下该章短剧/读者报告与该章之后的分支；全局人物状态改变则撤下全部依赖当前人物状态的分支。创作台“短剧与演播”页可按当前章节独立重建短剧、按当前策划与人物卡独立重建有声配置，不会重写正文；读者推演、剧情分支和商业宣发同样使用版本绑定的后台任务，请求入队前和 worker 调用模型前都会核对 revision。当前章没有短剧时明确显示为空，不会借用其他章节的短剧冒充当前结果。

想先验收界面且不影响真实数据，可运行：

```bash
python scripts/serve_demo.py --port 8766
```

打开 `http://127.0.0.1:8766`。演示作品、配置文件与自定义词库均在独立临时目录；模型传输被禁用，即使更改演示配置也不会调用供应商。演示中的“提取本章状态”使用确定性的本地结果，只用于走通交互和持久化，不代表真实模型质量。正常退出会清理临时数据；强制终止可能留下目录，启动日志会显示其路径。不要用它保存正式作品。原有 `examples/seed_demo_data.py` 会在实际作品目录中生成演示作品，两者用途不同。

## 💻 CLI 命令行使用方式

### 1. 一键全自动生产（从灵感到生成前 3 章黄金章节）

```bash
python main.py auto --name my_novel_01 --idea "主角穿越到诡异修仙界成为矿奴散修，金手指是只要触摸尸体就能回放对方死前三天的记忆并窃取遗留功法和隐秘" --genre "诡异修仙" --chapters 3
```

### 2. 仅执行小说策划与大纲构建

```bash
python main.py plan --name my_novel_01 --idea "主角拥有一家连接诸天万界的当铺，典当寿元和气运" --genre "诸天无限流" --volumes 3
```

`auto` 和 `plan` 是两种新建入口，不能对同一个已存在的项目重复执行；已有作品请使用下面的续写或恢复命令。新建不会忽略新创意并自动转为续写。`--chap-per-vol` 保留原命令名以兼容已有脚本，但实际含义是“第一卷初始连续细纲的最少章节数”；各卷完整长度由总纲内连续、互不重叠的 `chapter_range` 明确记录。

如果主策划或总纲任一阶段中断，可以从最后一次成功检查点恢复：

```bash
python main.py resume-plan --name my_novel_01
```

新建时会先保存有界的原始创意、题材、商业定位和规划参数；概念、世界观、人物三个模型阶段各自完成后独立提交。`resume-plan` 只调用缺失阶段：例如人物阶段失败，不会重新调用概念和世界观。人物完成后，三项结果才一次性晋升为正式设定；随后只恢复总纲，不生成正文。`continue-gen` 和网页“批量续写”也会先完成相同恢复，再生成请求章节，界面会标明待恢复阶段与额外模型费用。检查点随完整项目备份保存，但详情接口和状态输出不会返回原始创意文本；恢复前检查点内容为只读，避免改变后续模型输入。概念尚未生成的多个部分项目会用“未策划 · 项目标识”区分；零章节时正文编辑、细纲、重写和读者推演均原生禁用，完整备份仍可下载。

旧版中断项目若没有保存规划参数，需人工确认后同时指定 `--volumes` 和 `--chap-per-vol`。新的分阶段检查点已经绑定原请求，恢复时必须省略这些参数，不能换创意或更改规划。已存在总纲或正文的作品不会被重新初始化。

新项目的角色当前状态从各自的初始状态复制，而不是信任模型另给的“当前状态”。概念、世界观、人物各有独立持久化边界；完整人物检查点晋升为正式基础设定以及总纲发布分别使用原子事务。模型失败、非法人物阵容、保存故障和进程终止均不会形成半套正式设定。

滚动细纲不会跨卷，也不会覆盖后方已有细纲；章节、卷号和情绪节拍必须按请求范围一一对应，整块验证后才原子保存。旧总纲不被自动迁移或改写：若每卷已有章节锚点，仍可据此确定归属；若后续卷为空且没有 `chapter_range`，系统会停止并要求先人工明确转卷位置，不会继续把正文错误归入上一卷。超过总纲终章的续写同样会停止，需先由作者调整宏观规划。

### 3. 断点续写（从当前进度继续批量生成）

```bash
python main.py continue-gen --name my_novel_01 --count 5
```

### 4. 生成或重写指定单章

```bash
python main.py chapter --name my_novel_01 --num 4
```

新章必须是当前进度的下一章。若第 4 章已经存在，必须显式允许重写：

```bash
python main.py chapter --name my_novel_01 --num 4 --rewrite
```

命令退出码：`0` 表示命令成功；`1` 表示缺少项目/密钥或需要明确操作意图；`2` 表示参数或执行失败。批量失败会报告停止章节和已完成数量、保留已完成章节，并停止后续章节；不要忽略退出码而只根据输出文件是否存在判断成功。Python 调用 `generate_batch` 失败时会抛出 `BatchGenerationError`，可读取 `failed_chapter` 和 `completed_count`。

### 5. 查看小说实时状态看板（人设状态、当前境界、伏笔账本）

```bash
python main.py status --name my_novel_01
```

### 6. 查看本地所有小说项目

```bash
python main.py list
```

### 7. 导出全本 Markdown 排版文件

```bash
python main.py export --name my_novel_01
```

网页中的 TXT / Markdown / EPUB / ZIP 按钮会直接下载文件，不打开空白窗口。下载使用独立临时文件，不改动作品文件或版本号，因此不会使已打开的编辑窗口失效；传输结束或中断后会清理服务端临时文件。命令行导出仍会在作品目录生成发布稿。

手机窄屏下，章节目录会排列在正文上方。顶栏保留书架、命令面板和主题入口；打开作品后，命令面板不仅可进入「模型与 API 配置」，还会检索当前作品的正文、人物、伏笔、大纲、世界观与策划案，点击结果可直接跳到对应章节或视图。检索在服务端只读执行，不改变作品版本；输入变化或关闭面板会取消旧请求，迟到结果不能串到另一部作品。书架支持 Escape 关闭并返回入口按钮，关闭后不会继续占用键盘焦点。

## 🐍 Python 代码调用方式

可以在您自己的 Python 脚本或 Web 服务中直接引用 Pipeline：

```python
from pipeline.novel_pipeline import NovelPipeline

# 1. 创建或加载已有项目
pipeline = NovelPipeline(novel_id="xianxia_epic")

# 2. 策划小说与世界观
pipeline.initialize_new_novel(
    user_idea="一个靠吞噬天劫雷霆进化的废柴散修",
    genre_preference="传统仙侠",
    total_volumes=3,
    chapters_per_volume=10,
)

# 3. 批量生成章节
chapters = pipeline.generate_batch(start_chapter=1, count=3)

# 4. 获取汇总
summary = pipeline.get_status_summary()
print(f"书名: 《{summary['title']}》, 总字数: {summary['total_words']} 字")
```

测试作品使用独立临时目录，不写入真实作品库。多进程测试会启动短生命周期 Python 子进程验证真实文件锁，不调用模型服务。覆盖率包括 CLI 与 HTTP 入口，不能用单元测试通过代替浏览器、长篇性能或真实模型质量验证；页面还提供跳到主内容、具名作品库/章节导航地标、原生键盘控件和对比度门禁。剩余审计项见 [OPTIMIZATION_AUDIT.md](OPTIMIZATION_AUDIT.md)。

质量门禁会逐步复核源码、前端资产和依赖锁指纹；验收中途修改代码会判为失败。每次运行将结果保存到 `.quality/check-py<主版本>.<次版本>.json`，区分通过、失败、部分完成与未完成；缺少 Node.js 的验收不会标记为完整通过。报告不读取密钥或真实作品。

`.github/workflows/quality.yml` 在 Ubuntu、macOS、Windows 的 Python 3.11/3.14 矩阵中运行同一套锁定门禁，并用独立任务从 `package-lock.json` 重建前端资产、执行浏览器状态测试和高危漏洞审计；另一个任务在隔离演示服务上运行 Chromium、Firefox、WebKit 三引擎真实浏览器冒烟。工作流只授予仓库读取权限，第三方 Action 固定到完整提交 SHA，checkout 不保留凭据；测试环境使用空模型密钥、不可达的本机端点和 runner 临时作品目录。该配置已经过本地契约测试与 workflow 静态检查，但只有 GitHub 托管任务实际通过后，才能把对应系统列为已验证平台。

并发写入同一作品会明确返回忙碌（HTTP 423）；状态副本过期会返回冲突（HTTP 409），刷新后再操作。生成期间可以继续阅读。轻量加载或发现文件损坏的状态视图禁止写入，避免用缺失数据覆盖项目。

### 编辑版本与冲突保护

作品详情、章节正文和快照接口返回不透明的 `revision`。修改正文、段落、策划案、人物卡、大纲、合规替换、人工审阅、采纳分支、回滚、重命名、整章重写、从网页启动批量续写，以及运行读者推演、剧情分支或重建短剧、有声、商业宣发时，请在 JSON 中携带读取时的 `expected_revision`；删除使用 `If-Match` 请求头携带该 revision（64 位十六进制字符串）。这些后台任务会在模型调用前再次核对 revision。缺失前置版本返回 **428**，过期版本返回 **409**，不会覆盖新数据或消费过期任务的模型调用。旧版 API 集成需要更新请求；读者/分支接口现在返回 `status: started` 与 `task_id`，完成结果从作品详情和 `/api/status` 读取。

浏览器会自动携带版本，并将编辑器绑定到打开时的作品与章节；冲突时保留输入和弹窗。请先复制未保存内容，再刷新核对。切换作品、切章和轮询中的迟到响应不能替换当前页面。版本保护覆盖通过本应用进行的修改，不代表能防御绕过应用直接篡改文件。

保存编辑或后台任务完成后的局部刷新，会保留当前标签页、章节编号、展开的目录和阅读位置；主动从书架打开作品则进入阅读首页。原章节已不存在时选择邻近章节并回到开头，不把旧阅读位置套到其他章节上。工作区标签支持左右方向键与 Home/End，书架和目录可用键盘操作；段落手动编辑与 AI 重写按钮各自独立，不再重叠误触。

配置窗口在加载完成前不能编辑或保存。内容未变化的保存不会重写 `.env` 或重建模型客户端；修改时保留无关行、BOM 和换行风格，失败时恢复原始字节。

### 请求与资源边界

请求模型拒绝未知字段、布尔/小数伪装的整数、空字符、无效 Unicode、超长文本和过大的嵌套列表，不再静默截断或自动改成默认值。普通 JSON 请求上限 1 MiB；正文编辑相关请求上限 16 MiB；修改后的单章正文最多 2,000,000 个字符。验证错误不会回显提交的 API Key 或正文。

模型服务、插件式 Agent、文件解析或后台任务抛出的未知异常不会把供应商响应、模型原始输出、正文片段、异常注释或凭据复制到终端、任务状态、项目生成报告和 HTTP 响应。界面只显示固定说明与 12 位诊断编号；同一异常跨层传播时复用该编号。常规错误日志仅保留异常类型链、源码文件名/行号和经过摘要化的上下文，不记录异常消息、回溯局部变量或原始输入。由本应用明确标记的参数、并发和恢复提示仍会正常显示，便于用户自行处理。

备份导入只接受一个名为 `file` 的 multipart 文件，文件数据上限 500 MiB，multipart 额外开销上限 64 KiB。服务会核对声明大小和实际收到的分块，并对停滞、断连、残缺或畸形上传做清理。上传完成后直接复用受限临时文件校验，不再复制第二份。若反向代理位于本机服务之前，仍应在代理层配置等于或更小的请求体与超时限制。

磁盘 JSON 必须是普通文件，默认读取上限 128 MiB；符号链接、Windows 重解析点、管道/设备文件和超限数据会被拒绝。该限制用于阻止损坏或外部替换的文件拖垮本机进程，不是数据修复工具。

### 故障恢复与回收目录

章节保存、历史回滚和项目重命名现在使用多文件撤销日志。提交前中断会在下次加载时恢复到修改前的完整文件集合；已经提交则保留新版本。日志位于 `<OUTPUT_DIR>/.novelengine_transactions/`，校验失败会保留现场并拒绝继续写入，请勿直接删除仍待恢复的日志。创作台会显示不含本机路径的诊断编号、影响作品和安全处置顺序；归属已知的损坏只冻结相关作品，归属未知的事务现场会暂停全库写入、新建和导入，防止误覆盖。

“删除作品”现为移入 `<OUTPUT_DIR>/.novelengine_trash/`，不再立即清空文件。创作台的回收站可以查看并恢复作品；恢复时会校验项目身份、路径和目标冲突，绝不覆盖同名现存项目。当前不会自动清空回收目录。

事务最多备份本次变更涉及的 2 GiB 原文件；达到安全上限会停止并撤销本次修改。已验证异常与进程强制退出后的恢复，不把这些测试等同于物理断电或磁盘损坏保证。

### 历史重写与质检可信度

整章重写只使用目标章之前的人物状态、关系、伏笔和记忆，保留当前编辑后的世界观与大纲作为创作规划。现在人工设置的境界、地点、伤势和心情会自动记录“从当前第几章结束后生效”：不会倒灌进更早章节，也不会压过生效点之后真实发生的剧情事件；回滚同样排除未来覆盖。旧版没有日期的动态记录仍只作用于当前态，绝不猜测历史。缺少可靠章前快照或前序状态待补录时，会在调用模型前停止并说明原因；手动编辑和局部段落改文仍可使用。

旧项目缺少第 0 章证据时，创作台会先要求作者逐项核对“第 1 章开始前”的人物状态。界面只把已存人物卡的 `initial_state` 当候选，不会默认选中，不猜测关系、伏笔或后续人物；确认说明和旧时间线会连同校验清单一起归档。建立基线后，必须从第 1 章开始依次打开章节并点击“提取本章状态”。系统把该章现有正文发送给状态模型，只刷新事件、人物、关系、道具、伏笔、图谱与快照，正文及其质检/人工审阅历史保持不变。每次操作都绑定作品版本和下一待处理章节；失败、乱序或过期请求不会发布部分状态。此流程会产生状态模型调用费用，确认框会再次提示。

新状态事件记录对应正文的 SHA-256；事件身份、章节顺序、作品身份或正文摘要不匹配时，完整加载会转为只读保护。回滚界面会逐点显示精确、旧版近似或不可恢复状态，并禁用进度错配等不安全快照。现有两个旧示例项目仍保持原样，没有被自动推测、补写或改动；只有作者在自己的作品中明确确认后，修复才会开始。

质检报告现在绑定实际送审正文。通过稿优先于高分未通过稿；润色改变正文后增加一次复检，不通过、服务失败或返回空文时保留原稿。整章重写会合并保留旧机器质检和人工审阅历史。阅读器的“审阅记录”可查看每次机器检查的问题、指令和对应正文摘要，并记录“认可当前版本”或“需要修改”的人工结论。人工结论同样绑定当前正文 SHA-256；正文变化后自动转为历史记录，不会伪装成对新版正文的认可。状态抽取失败时正文与待补录标记一起保存，后续自动写作暂停；可在正文不变的前提下从最早待补录章依次重新提取。

1. **去 AI 味规则库定制**：
   - 可以在 [`config/anti_ai_rules.py`](config/anti_ai_rules.py) 中增加针对特定题材的禁忌词与修辞引导。

   - 在 `.env` 中，您可以将 `WRITER_MODEL` 设为文学表述能力最强的模型（如 `claude-3-5-sonnet`），将 `CRITIC_MODEL` 设为 `deepseek-reasoner` / `o1`，将 `STATE_MODEL` 设为高性价比模型（如 `deepseek-chat` / `gpt-4o-mini`）。
